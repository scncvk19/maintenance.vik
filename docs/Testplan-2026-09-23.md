# maintenance.vik – vollständiger Testplan für den 23. September 2026

**Ziel:** Den aktuellen Funktionsstand vollständig in einer **isolierten Testinstallation** prüfen. Produktive Daten und produktive Docker-Volumes werden nicht für destruktive Tests verwendet.

## 1. Vor dem Start

1. In `N:\maintenance.vik`:
   ```powershell
   git status --short
   git pull --ff-only
   ```
   Bei lokalen Änderungen zuerst stoppen und prüfen; kein `git reset --hard`.

2. Vor jedem Restore-Test ein geprüftes Produktiv-Backup besitzen. ZIP plus `.sha256` kontrollieren und zusätzlich auf einem anderen Datenträger sichern.

3. Separate Testkopie vorbereiten:
   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik\scripts\Prepare-TestEnvironment.ps1"
   ```
   Erwartung: `N:\maintenance.vik-test`, eigene `.env`, `APP_PORT=3100`.

4. Testcontainer starten:
   ```powershell
   docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test up -d --build --wait --wait-timeout 300
   docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test ps
   ```
   Alle Volumes müssen das Präfix `maintenance-vik-test` tragen.

## 2. Kernfunktionen

|---|---|---|

| 2 | Test-Immobilie, Grundstück/Anlage und Test-Fahrzeug anlegen | Daten bleiben nach Neuladen erhalten. |
| 3 | Räume/Komponenten anlegen und zuordnen | Beziehungen stimmen. |

## 3. Lokale Dokumentanalyse / OCR

1. Je ein selbst erstelltes TXT, Text-PDF und Bild/Scan hochladen.
2. In der Dokumentkarte **Lokal analysieren** wählen.
3. Prüfen:
   - Textvorschau entsteht lokal.
   - Bei eindeutiger Kategorie erscheint ein Vorschlag.
   - Ohne Bestätigung wird nichts gespeichert.
   - Nach Bestätigung ändert sich nur die Kategorie.
   - Schlecht lesbare Scans dürfen ohne eindeutigen Vorschlag enden.
4. Keine sensiblen Testinhalte verwenden. Die Analyse ist auf 10 MB und maximal drei PDF-Seiten begrenzt.

## 4. Steuer-Tresor

Nur Testdaten verwenden.

1. Tresor mit neuem Testpasswort einrichten.
2. Steuerfall/Testanhang anlegen.
3. Sperren und mit Passwort erneut öffnen.
4. Wiederherstellungscode erzeugen und sicher notieren.
5. Passwortzugriff erneut prüfen.
6. Recovery ausschließlich im Test-Tresor ausprobieren.
7. Recovery-Code und Passwörter nicht in Screenshots/Chat posten.

## 5. Lokale Benutzerkonten und Rollen

Im **Testordner**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik-test\scripts\Set-AppUser.ps1" -UserName admin-test -Role admin -ProjectDirectory "N:\maintenance.vik-test"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik-test\scripts\Set-AppUser.ps1" -UserName leser-test -Role viewer -ProjectDirectory "N:\maintenance.vik-test"
docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test up -d --build
```

Prüfen:
- Ohne Sitzung Weiterleitung zu `/login`.
- Falsches Passwort abgewiesen.
- Admin kann lesen und ändern.
- Leser kann normale Daten lesen.
- Leser bekommt bei Änderungen, Backup und Steuerbereich HTTP 403.
- `/logout` beendet die Sitzung.
- Keine Testpasswörter weitergeben.

## 6. Normales ZIP-Backup bis 250 MB

1. In der Testinstanz Backup exportieren.
2. ZIP und SHA-256 prüfen.
3. Testdatensatz nach dem Export verändern.
4. **Nur in der Testinstanz** Backup-Vorschau und Import ausführen.
5. Prüfen:
   - ursprüngliche Daten wiederhergestellt,
   - Dokumente intakt,
   - alte Steuer-Tresor-Sitzung ungültig.
6. Niemals den Backup-Import auf der Produktivinstanz ausprobieren.

## 7. Großbackup und Großrestore

Das normale API-ZIP bleibt bewusst auf 250 MB begrenzt. Größere Bestände nutzen den Offline-Weg.

Großbackup ausschließlich aus der Testinstanz:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik-test\scripts\Backup-Large.ps1" -ComposeProject maintenance-vik-test -Destination "E:\maintenance-vik-test-backups"
```

Integrität prüfen:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik-test\scripts\Verify-LargeBackup.ps1" -BackupDirectory "E:\maintenance-vik-test-backups\maintenance-vik-offline-<Zeitstempel>"
```

Danach Testdaten sichtbar verändern und **nur im Projekt mit Suffix `-test`** wiederherstellen:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "N:\maintenance.vik-test\scripts\Restore-Large.ps1" -BackupDirectory "E:\maintenance-vik-test-backups\maintenance-vik-offline-<Zeitstempel>" -ComposeProject maintenance-vik-test -Confirmation RESTORE_ISOLATED_TEST
```

Erwartung: Datenbank und Dokumente entsprechen wieder dem Sicherungsstand. Das Skript muss den Produktivnamen `maintenance-vik` verweigern.

## 8. Telegram – optionaler Realtest

Ohne eigenen Test-Bot **überspringen**, nicht als Fehler werten.

Mit Test-Bot:
1. Test-Token und Test-Chat-ID ausschließlich in `N:\maintenance.vik-test\.env` eintragen.
2. `TELEGRAM_SEND_ENABLED=YES_I_CONFIGURED_THE_BOT`.
3. Testcontainer neu erstellen.
4. Telegram-Vorschau in Einstellungen laden.
5. Eine Nachricht ausdrücklich bestätigen.
6. Erwartung: Es werden nur Anzahlen gesendet, keine Titel, Adressen, Beträge oder Steuerinhalte.
7. Zweiter Versand am selben Tag an denselben Chat wird dedupliziert.

## 9. WhatsApp Cloud API – optionaler Realtest

Ohne Meta-Testkonto, Testempfänger und freigegebenes Template **überspringen**, nicht als Fehler werten.

Benötigte Testwerte in der Test-`.env`: `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_GRAPH_VERSION`, `WHATSAPP_TEMPLATE_NAME`, `WHATSAPP_TEMPLATE_LANGUAGE` und `WHATSAPP_SEND_ENABLED=YES_I_CONFIGURED_WHATSAPP`.

Das Template hat drei Body-Parameter: Aufgaben/Wartungen, Vertragsenden, Dokumenterinnerungen.

Prüfen:
- Status zeigt Provider aktiv.
- Versand verlangt ausdrückliche Bestätigung.
- Empfänger erhält nur die drei Anzahlen.
- Zweiter Versand am selben Tag wird dedupliziert.

## 10. HTTPS – optionaler LAN/VPN-Test

1. In der Test-`.env` einen erreichbaren Testnamen als `APP_HOSTNAME` setzen.
2. Start mit Overlay:
   ```powershell
   docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test -f "N:\maintenance.vik-test\docker-compose.yml" -f "N:\maintenance.vik-test\docker-compose.https.yml" up -d --build
   ```
3. `https://<APP_HOSTNAME>/` öffnen.
4. Caddy nutzt eine interne CA. Auf einem anderen Gerät ist eine Zertifikatswarnung normal, bis die Root-CA bewusst auf diesem Testgerät vertraut wird.
5. Port 3000 nicht ins LAN veröffentlichen.

## 11. Neustart/Persistenz

```powershell
docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test restart
```

Danach prüfen: Assets, Termine, Finanzen, Verträge, Dokumente und Benutzerzugriff bleiben erhalten.

## Stop-Kriterien

Sofort abbrechen bei:
- Docker-Projektname ohne `-test` bei Restore,
- unerwarteten Produktiv-Volumes,
- fehlerhafter Prüfsumme,
- beschädigtem Backup,
- produktiven Tokens/Passwörtern in der Test-`.env`,
- einem Skript, das `docker compose down -v` gegen `maintenance-vik` vorschlägt.

## Nach dem Test

Fehler mit Schritt, Uhrzeit, Erwartung und tatsächlicher Meldung notieren. Für Logs nur die Testinstanz verwenden:

```powershell
docker compose --project-directory "N:\maintenance.vik-test" -p maintenance-vik-test logs --tail=150
```

Vor dem Teilen Tokens, Passwörter, Chat-IDs, Rufnummern, Adressen und Steuerdaten entfernen. Produktivcontainer während der Abnahme unverändert lassen.
